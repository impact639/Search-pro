## 二、确认的根因（附证据）

### P2-1　回答慢的根因是「模型 + 链路」双重叠加
- **模型层**：默认配置 `deepseek-reasoner`（`CommonViewModel.DEFAULT_MODEL_NAME`），是深度推理模型，首字输出前要经历较长推理，与「查词/解题要快」的预期不符。**建议默认改用快模型**（如 `deepseek-chat`），属于配置项，无需改代码。
- **链路层**：旧 `sendStream` 未区分「首个网络字节」与「首个可显示文字」；未设置流式读超时；无取消入口；无加载态，导致用户看到的是「点了提问 → 长时间空白 → 突然整段出现」。

### P2-2　SSE 解析不标准
- 旧实现把原始行直接当作 JSON 解析，遇到 OpenAI 兼容接口的 `data: {…}` 前缀、`[DONE]`、空行/注释行时会产生解析噪声或提前结束。
- 证据：`HttpControl.kt` 历史版本直接 `onChunkReceived(line)`，未剥离 `data:` 前缀。

### P3-1　分享过滤过窄
- `AndroidManifest.xml` 原为 `data android:mimeType="text/plain"`，部分 App 以 `text/html`、`text/plain; charset=utf-8` 分享纯文本会被系统判定不匹配。
- 已改为 `text/*`，并在 `handleShareIntent` 用 `intent.type?.startsWith("text/")` 二次校验。

### P3-2　分享文字覆盖用户未提交内容
- 旧逻辑 `updateQuestionText(sharedText)` 直接覆盖，用户正在编辑的问题会被冲掉。
- 已改为：空白时填入、非空白时换行追加（与划词一致）。

### P4　OCR 缺位
- 原 App 只能靠「读屏」（无障碍遍历）或手动输入获取题目，无法应对图片/不可选中文本场景。

### P1　微信/QQ 划词失效（机制性限制）
- **证据**：笔记、浏览器等使用系统标准文本选区，能触发 `TYPE_VIEW_TEXT_SELECTION_CHANGED`；微信/QQ 的聊天文本是自绘选区，不走系统 `AccessibilityNodeInfo` 的 textSelectionStart/End，也不发标准选区事件。
- **结论**：属于第三方实现方式导致的限制，App 内无法用无障碍方式根治。**替代方案已落地为 P4 识屏 OCR**，覆盖微信/QQ 内不可选中文本的场景。

## 三、本轮改动清单

### 1. `control/HttpControl.kt`（P2，重写）
- 拆分 `client`（非流式，60s 读超时）与 `streamClient`（流式，300s 读超时 + 600s 整体超时，禁用自动重试）。
- `activeCall` + `cancel()`：关闭浮窗/重新提问时取消进行中的请求。
- `parseSse()`：标准 SSE 解析——只取 `data:` 行、跳过 `event:`/`id:`/注释/空行、识别 `[DONE]`。
- 全链路耗时埋点（`Log.d("ScanSearchTime", …)`），**只记耗时/状态码/错误类别，不记 API Key、Authorization、对话内容**。

### 2. `ui/FloatingWindowContent.kt`（P2/P3/P4/P5/P6）
- 提交时 `HttpControl.cancel()` 取消旧请求；`loading` 状态 + 「正在生成回答…」提示；首字到达即取消加载态。
- 划词/分享统一「追加不覆盖」语义。
- 新增「识屏」按钮 → 收起浮窗 → 启动 `ScreenCaptureActivity`。
- 流式回调只取 `delta.content`，忽略 `reasoning_content`（去思考过程）。

### 3. `control/FxComposeControl.kt`（P2/P4）
- `cancel()` 增加 `HttpControl.cancel()`。
- 新增 `showSearchWindow()`：OCR 回填后仅显示已装主浮窗（无需 `CommonViewModel`）。

### 4. `MainActivity.kt`（P3）
- `onNewIntent` 处理 `singleTask` 下的分享投递；`handleShareIntent` 从 `text/*` 提取 `EXTRA_TEXT`，空/异常直接丢弃，推入统一通道。

### 5. `config/StaticVariableConfig.kt`（P3/P6）
- 新增 `SharedTextEvent(seq, text)` + `sharedTextFlow`：`seq` 自增区分重复分享，避免 StateFlow 对相同值去重导致重复分享丢失。

### 6. `ScreenCaptureActivity.kt`（P4，新增）
- MediaProjection 授权 → 捕获一帧 → 全屏截图框选（Canvas 拖拽）→ ML Kit 中文识别 → 回填输入框。

### 7. `service/ScreenCaptureService.kt`（P4，新增）
- Android 14（targetSdk 34）要求：`getMediaProjection()` 前必须有 `foregroundServiceType="mediaProjection"` 前台服务，否则抛 `SecurityException`。

### 8. `service/ScreenReaderService.kt`（P1，上一轮）
- 划词事件在 `openScan` 门禁**之前**处理，避免进程重启后门禁复位导致划词失效。

### 9. `AndroidManifest.xml` / `build.gradle.kts` / `libs.versions.toml`（P3/P4）
- 权限：`FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_MEDIA_PROJECTION`、`POST_NOTIFICATIONS`。
- 分享 MIME 放宽 `text/*`；注册 `ScreenCaptureActivity` / `ScreenCaptureService`。
- 依赖：`com.google.mlkit:text-recognition-chinese:16.0.1`（离线中文模型，无需联网）。

## 五、真机手动测试步骤

1. **构建**：`./gradlew assembleDebug`，或从 CI 下载 debug APK。
2. **安装**：`adb install -r app/build/outputs/apk/debug/app-debug.apk`。
3. **划词**（笔记/浏览器）：选中文字 → 观察悬浮窗输入框是否自动填入；再次选中 → 是否追加不覆盖。
4. **分享**：在浏览器/笔记里「分享」一段文字 → 选「问一下」→ 输入框是否填入；再次分享 → 是否追加。
5. **识屏**：打开微信/QQ 或一张图片 → 点浮窗「识屏」→ 授权屏幕捕获 → 框选区域 → 点「识别」→ 结果是否回填输入框。
6. **延迟诊断**：`adb logcat -s ScanSearchTime`，触发一次提问，记录「响应头到达 / 首个数据块 / 首个有效文字 / 完整回答结束」各段耗时。
7. **取消**：提问进行中关闭浮窗或再次提问，确认旧请求被取消、无串流。
8. **思考过程**：确认回答不再出现 `reasoning_content` 内容，只显示「详细讲解 / 最终答案」。

## 六、已知限制

1. **微信/QQ 划词**：自绘选区不走系统无障碍，需改用「识屏 OCR」。
2. **数学公式 OCR**：ML Kit 是通用文字识别，公式、上下标、多栏混排识别率低；识别出公式后由模型用 LaTeX 二次解读，可能出错。
3. **识屏授权**：每次框选都走系统屏幕捕获授权弹窗（Android 安全设计，无法静默）；Android 14+ 需前台服务通知。
4. **重复划词去重**：`selectedTextFlow` 为 `StateFlow`，连续两次选中完全相同文字时第二次不会重新触发（`sharedTextFlow` 已用 `seq` 规避此问题；划词路径为低频边缘情况，暂未加 `seq`）。
5. **默认模型**：`deepseek-reasoner` 首字慢；建议用户在配置里改成快模型以获得更短等待。
6. **无真机验证**：OCR/MediaProjection 链路未经真机运行，见 4.2。
